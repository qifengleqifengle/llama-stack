# 项目简历表述与问答说明

## 简历部分

### 项目名称

RAG 知识库检索系统

### 技术栈

`Python`、`OpenGauss 向量检索适配设计`、`PostgreSQL`、`BM25`、`Llama Stack`、`Query Rewrite`、`混合检索重排（RRF / Weighted）`、`对话记忆管理（滑动窗口）`

### 项目描述

作为开源之夏（openGauss 社区）项目参与者，我主要负责从 Llama Stack 基础层能力对接到应用层 RAG 落地的整体推进，聚焦技术文档场景下的检索稳定性、对话连续性与答案可追溯性。

### 核心亮点

- 参与 `remote::opengauss` 向量库能力建设，完善检索抽象并支持 `vector / keyword / hybrid` 多路召回。
- 基于 openGauss 原生 BM25/全文检索能力接入关键词检索路径，并通过 `RRF / Weighted` 与向量检索做混合重排，提升技术文档问答场景下的检索稳定性。
- 结合文档结构设计多策略分块（结构分块、固定长度、固定字符、递归分块），提升检索单元的语义完整性与可命中性。
- 实现 Query Rewrite 与滑动窗口记忆协同机制，在检索前完成上下文补全与查询标准化，提升跨轮问题的检索命中质量。
- 基于文档语料开展 `vector`、`keyword`、`hybrid`、`rewrite + hybrid` 的策略对比验证，沉淀面向不同问题类型的检索选型结论。

### 推荐口径

建议统一按“两层架构”开场：

- 基础层：做向量检索、BM25 关键词检索、hybrid 重排与 provider 适配。
- 应用层：做文档解析入库、分块、查询改写、滑动窗口记忆、对话问答与策略对比评估。
- 结论先讲策略：`hybrid` 更稳，`rewrite + hybrid` 在复杂问题上更有优势。

## 面试拷打问答（RAG 方向）

下面是按“面试官高压深挖”整理的问题与回答，你可以直接用于模拟面试。

### Q1：你这个项目到底做了什么，30 秒说清楚。

**答：**

我做的是一个两层架构的 RAG 系统。基础层负责检索引擎能力，包括向量检索、BM25 关键词检索和 hybrid 重排；应用层负责把能力产品化，包括文档解析入库、分块、查询改写、滑动窗口记忆和带引用对话。我的核心目标是提升技术问答场景下的召回稳定性和回答可追溯性。

### Q2：为什么要做 `vector + keyword + hybrid`，只做向量不行吗？

**答：**

只做向量会在术语、版本号、参数名这类精确词匹配场景下漏召回。只做关键词又会在语义改写、同义表达和口语化问题上表现不稳。`hybrid` 的价值是同时保留语义召回和词面召回，工程上通常更稳，尤其是技术文档问答这种既有术语又有语义表达变化的场景。

### Q3：你说的 BM25 在你系统里解决了什么问题？

**答：**

BM25 主要解决“关键词精确命中”的问题，尤其是产品名、函数名、配置项、报错关键字、版本号等。我的实践是把 BM25 作为关键词路径，再和向量路径做混合重排，避免单一路径偏置。

### Q4：hybrid 重排你为什么用了两种方式（RRF / Weighted）？

**答：**

两种方式对应不同需求：RRF 更稳健、参数敏感度低，适合作为默认方案；Weighted 可控性更强，适合在已知业务偏好下调节“语义召回”和“关键词召回”的权重。我的做法是默认 RRF，特定场景再切 Weighted。

### Q5：Query Rewrite 到底怎么做，为什么有效？

**答：**

Query Rewrite 是检索前处理，不是回答问题。核心约束是保留用户意图和关键实体，去掉冗余口语表达，把问题改写成更适合检索的一条查询。它有效的原因是降低了用户表达噪声，提升了 query 与文档表达的匹配度，尤其对复杂问题和多跳问题更明显。

### Q6：你提到“记忆管理”，具体怎么落地？

**答：**

我用的是滑动窗口记忆：维护最近若干轮对话作为短期上下文，并在查询改写和检索阶段注入上下文。这样用户说“这个参数”“刚才那个报错”时，系统能恢复指代，减少跨轮语义漂移。简单说就是让改写和检索都能看到“最近发生了什么”。

### Q7：为什么把记忆接在改写和检索阶段，而不是只放在回答阶段？

**答：**

RAG 的上限在检索，不在生成。只在回答阶段看历史，可能已经错过正确证据。把记忆前置到改写和检索阶段，能先把 query 变准确，再把证据召回准确，后面的回答自然更稳。

### Q8：你是怎么做文档解析和分块的？

**答：**

我接入 MinerU 做 URL/文件解析，拿到结构化 Markdown 后做分块。分块不是单一策略，而是按文档特点选择结构分块、固定长度、固定字符或递归分块。这样做是为了尽量保留语义边界，同时控制 chunk 粒度，减少索引和召回阶段的信息损失。

### Q9：为什么分块会影响最终问答效果？

**答：**

分块决定了检索单元。块太粗会把噪声带进来，块太细会打断语义。技术文档通常有强结构，保留标题-段落层次可以让检索结果更可解释，也更容易让回答附带可靠引用。

### Q10：你怎么验证“哪种策略更好”？

**答：**

我做的是策略对比验证，不强调单一分数：准备一组技术文档和按类型分桶的问题集，对 `vector`、`keyword`、`hybrid`、`rewrite + hybrid` 做案例级对比，重点看证据命中是否稳定、回答是否可追溯、不同问题类型下哪条策略更适配。结论通常是：hybrid 整体更稳，rewrite + hybrid 在复杂问题上更有优势。

### Q11：如果面试官追问“你最大的工程取舍是什么”？

**答：**

我的取舍是优先可落地和可解释，而不是一上来追求复杂算法。具体是先把基础检索链路和应用闭环打通，再在改写、记忆、分块和重排上做可控增强。这样能快速形成可演示、可迭代的系统。

### Q12：如果再给你 2 周，你会先补什么？

**答：**

我会优先补三件事：

1. 记忆管理从纯滑动窗口升级为“窗口 + 摘要记忆”。
2. 检索策略增加更细粒度路由规则（按问题类型自动切换）。
3. 增加更系统的对比样例与错误归因模板，提升策略迭代效率。

## 原理级深挖手册（从总到细）

### 1）BM25 关键词检索原理（面试可讲版）

BM25 的核心思想是：一个词在当前文档里出现越多、在全库里越稀有、且文档长度不过分偏大，则该文档相关性越高。

可背公式：

$$
	ext{score}(D,Q)=\sum_{q_i\in Q} \text{IDF}(q_i)\cdot
\frac{f(q_i,D)\cdot (k_1+1)}{f(q_i,D)+k_1\cdot(1-b+b\cdot |D|/\text{avgdl})}
$$

- $f(q_i,D)$：词 $q_i$ 在文档 $D$ 的词频。
- $|D|/\text{avgdl}$：长度归一化，避免长文档天然占优。
- $k_1,b$：控制词频饱和和长度惩罚。

一句话：BM25 是“词频 + 稀有度 + 长度归一化”的平衡。

### 2）RRF / Weighted 重排原理

#### RRF（Reciprocal Rank Fusion）

当你有多路召回结果（向量、关键词）时，RRF 不直接看原始分数，而看每一路的排名位置：

$$
	ext{RRF}(d)=\sum_{r\in R}\frac{1}{k+\text{rank}_r(d)}
$$

- 优点：稳健、对不同打分尺度不敏感。
- 适用：默认方案，工程上更抗噪。

#### Weighted 融合

先把两路分数归一化，再按权重融合：

$$
	ext{score}(d)=\alpha\cdot s_{vec}(d)+(1-\alpha)\cdot s_{kw}(d)
$$

- 优点：可控性强，可按业务调节语义 vs 词面。
- 风险：对分数校准更敏感。

### 3）HNSW 向量索引原理（你说的 HSW 实际通常是 HNSW）

面试官如果问“HSW 是什么”，你可以先纠正为 HNSW（Hierarchical Navigable Small World）。

- 本质：分层小世界图近邻搜索。
- 建图：每个向量连若干近邻边，顶层稀疏、底层稠密。
- 查询：从高层贪心下沉到低层，再做局部扩展搜索。

常见参数：

- `M`：每个节点最大连接数，越大召回潜力越高但内存更大。
- `efConstruction`：建图搜索宽度，越大索引质量更好但构建更慢。
- `efSearch`：查询搜索宽度，越大效果更好但时延更高。

工程取舍：用 `efSearch` 在“效果-时延”之间动态调优最常见。

### 4）切块（Chunking）原理与取舍

切块目标不是“切得均匀”，而是“让检索单元语义完整且可命中”。

- 结构分块：保留标题/段落边界，适合技术文档。
- 固定长度：实现简单，吞吐稳定，适合 baseline。
- 固定字符：适合中英混排、token 不稳定场景。
- 递归分块：先粗切再细切，兼顾语义完整与粒度控制。

高频追问回答：

- 为什么不用单一切块？因为不同文档结构差异很大，单策略会系统性漏召回。
- 为什么切块影响最终答案？因为检索的最小证据单元就是 chunk。

### 5）Query Rewrite 原理

Query Rewrite 是“检索前标准化”，核心是降噪和补全上下文，不是回答问题。

改写约束可背：

- 保留实体名、版本号、错误码、参数名。
- 保留用户意图，不引入新事实。
- 单条查询输出，不扩写成多问题。

失败兜底：改写失败或异常时回退原 query，保证链路可用性。

### 6）记忆管理原理（滑动窗口）

你当前口径可讲“短期记忆优先”：

- 用最近 $K$ 轮对话作为窗口记忆。
- 控制 token budget，超限时优先保留最近轮与关键实体轮。
- 在改写和检索阶段注入窗口，解决跨轮指代（“这个参数”“刚才那个报错”）。

进阶口径（可作为后续计划）：

- 窗口 + 摘要记忆（长期）双层结构。
- 关键事实单独抽取为 profile memory，避免被窗口截断。

### 7）端到端链路（一句话讲全）

用户问题进入后，先加载滑动窗口记忆做 Query Rewrite，再走向量/BM25 多路召回与 hybrid 重排，最后在证据约束下生成回答并返回引用。

## 细节拷打问答（Q13 ~ Q20）

### Q13：你怎么避免 Query Rewrite 把问题改坏？

**答：**

我做了三层约束：提示词约束（实体和意图保留）、输出形态约束（只输出一条查询）、失败兜底（异常直接回退原 query）。所以改写是“增强项”而不是单点风险。

### Q14：什么时候你会放弃 hybrid，改用单路检索？

**答：**

当场景明确是精确术语匹配时，我会偏关键词路径；当问题语义改写明显、词面不稳定时偏向向量路径。默认仍是 hybrid，因为整体鲁棒性更好。

### Q15：RRF 和 Weighted 的核心差异一句话怎么说？

**答：**

RRF 看“名次”，更稳；Weighted 看“分数”，更可控。

### Q16：HNSW 参数你先调哪个？为什么？

**答：**

我先调 `efSearch`，因为它直接影响线上查询效果和时延，改动成本最低；`M` 和 `efConstruction` 更偏索引构建阶段，通常不先动。

### Q17：切块大小怎么定？

**答：**

先按文档类型给默认值，再用小样本看“证据是否被切断”和“检索噪声是否升高”。如果证据跨块严重就增大块；如果无关内容太多就减小块或改递归策略。

### Q18：你怎么解释“记忆前置到检索”这个设计？

**答：**

因为 RAG 的瓶颈先在召回，不在生成。先把 query 理解对、证据找对，再谈回答质量。只在生成阶段加记忆通常已经错过正确证据。

### Q19：如果面试官问你“有没有绝对最优策略”，你怎么答？

**答：**

没有绝对最优，只有场景最优。我的方法是按问题类型做策略对比和路由：术语密集型偏关键词，语义表达型偏向量，通用场景用 hybrid。

### Q20：你如何证明这个系统“可解释”？

**答：**

我要求回答尽量绑定检索证据，并能回看每次策略选择（改写、召回路径、重排结果）。这样可以解释“为什么是这个答案”，而不只是“模型说了什么”。
